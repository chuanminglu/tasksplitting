## 一、我们在验证什么，为什么

`VueReact+Java专用Harness商业方案.md` 提出一个商业假设：任务拆细+SDD写清+四道门禁后，17B~30B级本地模型能承接约80%的开发任务，20%硬骨头才上70B+云端模型，从而把AI编码账单降到1/5。这个假设能否成立，取决于Phase 0要跑出的两个数字：

| 数字 | 达标线 | 回炉线 |
|---|---|---|
| 一次通过率（真实任务抽样，spec-verifier一次绿） | ≥80% | <60% |
| 成本压缩比（纯70B vs 17B+校验+升级） | ≥1:5 | 未达标则经济性不成立 |

这两个数字不出来，后面"要不要拿这个方案去找客户/融资"都无从谈起。本报告要回答的核心问题是：**我们现在离能负责任地回答这两个数字，还差多远**。

## 三、目前掌握的证据（诚实边界）

### 强信号
- **33/33任务一次通过，0次人工介入**（第一轮6个 + 本轮新增27个），文件命中率：26/27任务的"必须改动"清单100%命中（唯一例外`T00302`因前置任务已实现而无需改动）；范围蔓延0次；升级率0
- **样本覆盖从1个标签扩到6个标签**：本轮首次覆盖`test-generation`（8个）、`simple-ui`（9个）、`config`（5个）三个此前完全没测过的标签，三个标签均0失败；`crud`（3个）与`business-logic`（6个）在新增样本上同样0失败
- 覆盖了`novel-design`（T00101，从零设计鉴权方案）和`refactor`（T00106，接入既有Controller）——这两类商业方案原本判给**70B+档位**的任务，27B模型独立完成，且是在零人工干预下
- 更进一步：两轮合计**7处任务说明本身的真实缺陷**被自主发现并修复（第一轮2处：技术断言错误、结构覆盖遗漏；本轮5处：`npm ci`在npm workspaces下不可用、SQLite的`ADD COLUMN IF NOT EXISTS`不支持（**第一轮同坑重演**）、`T00302`跨任务预测失准、`T-CFG-04`新机制环境约束未预判、`T00203`既有数据模型认知不全）。任务说明缺陷密度从第一轮0.33/任务降至**0.15/任务**（下降约55%）

### 完全空白
- **成本压缩比**：两轮共33份报告**均未采集**生成侧token/耗时数据，也没有对应的Spring Boot技术栈基线可比——Phase 0要求的两个数字，这一个目前仍是**0数据**（`StackHarness-Phase0数据补齐执行计划.md`工作流A尚未执行）
- **spec-verifier口径**：本轮判定标准仍是"测试命令通过+人工核对DoD"，比商业方案真正要求的"spec-verifier一次绿"更宽松，尚不知道换成严格口径后数字会不会掉

### 统计上不可靠
- **样本量仍不足**：33个 vs 方案建议的40+，且细分标签未达标——`test-generation`（8）与`simple-ui`（9）**已达标**，但`crud`/`config`（合并计8，缺4）与`business-logic`（6，缺6）**未达标**，核心样本合计31/40
- 仍**集中在单一仓库、单一技术栈**（`tasksplitting`，Spring Boot + React）；商业方案还覆盖Vue组件
- 33个任务中**27个来自同一条计划、且后序任务天然受益于前序任务打下的地基**（`T00302`是极端例子——地基好到"无需改动"即可交付），**置信区间依然偏宽，不能据此下"达标"或"不达标"的结论**
