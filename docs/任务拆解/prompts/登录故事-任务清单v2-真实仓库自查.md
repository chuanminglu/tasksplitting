**故事描述**：作为一名系统用户，我希望能够使用用户名和密码登录系统，登录成功后进入我的工作台，以便安全地访问只属于我的功能和数据。（原文已是"作为...我希望...以便..."标准形态，未转写）目前系统还没有任何登录/鉴权机制。

**调查过程**（自查对象：`/tmp/benchmark-repo/tasksplitting`，浅克隆自 `chuanminglu/tasksplitting` main 分支 commit `fe2c129`）：

**模式判断**：**Walking Skeleton**（走通骨架法：先搭一条最薄的端到端路径跑通，再逐片加厚功能，全程用特性开关包裹到验收通过再对外开放）。
依据：`[FACT]` 上述七项自查一致显示代码库里不存在任何"已在生产环境跑着、不能说停就停"的旧登录/鉴权实现（无User模型、无鉴权路由、无相关依赖、无相关历史提交）。不满足 **Expand-Contract**（新旧并存迁移法：Expand新增新路径与旧实现并存→Migrate调用方逐个切换→Contract确认无依赖后删旧代码）的适用前提——该模式要求"旧实现"存在。因此本故事是纯新增能力，选 Walking Skeleton。

## 如何生成单任务实现说明

以上任务清单是规划阶段的路线图，颗粒度只到"任务名+验收标准要点+对应AC+预计涉及文件概要+路由建议标签"。某条具体任务（如 `T00101`）真正要派发给执行者前，使用 `单任务实现-subagent提示词.md`，把这条任务的完整条目 + 所属故事 US-AUTH-01 的模式判断（Walking Skeleton）/Feature Flag上下文（`login_auth_enabled`）+ **当下最新的 REPO_PATH 自查结果**（不是本次规划时基于 commit `fe2c129` 的自查结果，而是派发时刻的最新代码库状态）喂进去，现场生成一份完整自包含的实现说明再派发。T00102～T00106 均依赖前序任务（尤其 T00101 建立的 User model 与 `/api/login` 路由）实际合并后的真实文件状态，生成说明时要把前序任务"实际改了哪些文件"作为材料，而不是沿用本总览里基于 `[INFER]` 标注的预判。
