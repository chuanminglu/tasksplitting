**33 个任务全部一次通过，0 次人工修改、0 次重试、0 次升级、0 次范围蔓延。** 第一轮的"6/6"在本轮获得显著扩样支持：新覆盖的 `test-generation`（8个）、`simple-ui`（9个）、`config`（5个）三个**此前完全没测过的标签**同样零失败，`crud`/`business-logic` 也在新增样本上保持零失败。

比通过率更有信息量的是本轮的**过程性发现**：

1. **任务说明本身仍有 3 处真实缺陷**（第 4a 及第 3 阶段暴露 2 处重演性缺陷：`npm ci` 在 npm workspaces 下不可用、`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 在 SQLite 下不被支持——后者正是第一轮 T00103 已经踩过的同一个坑），**全部由执行方自主诊断 + 自主修复，零人工介入**。这说明"自愈能力"在 4 倍样本量下仍然稳定复现，不是第一轮的偶然。
2. **跨任务预测失准 1 处**：`T00302` 的"预计涉及文件"预测 `App.tsx` 必须改动，实际前置任务 `T00301` 已实现完毕，该任务最终只交付了测试文件——**任务说明在展开时未核对前置任务的真实交付结果**，这是一个前两轮未曾暴露的新缺陷类型（见第七节）。
3. **"可能改动（依赖当场决策）"档的判断 4/4 全对**，且包含 2 次"判定为不需要改"的正确判断（`T-UI-02` 的 `styles.css`、`T-CFG-03` 的 `application.yml`）——这条 v2 引入的机制在 27 个新样本上继续成立。

**结论定位：本轮把"一次通过率"这一维度从 6 个样本推到 33 个样本、6 个标签，全部零失败；但成本压缩比依然 0 数据（工作流 A 未执行），且样本分层仍有 2 个标签未达门槛。Phase 0 的两个数字，目前仍只有半个。**

## 五、返工率与"自愈循环"

### 5.1 返工（需人工纠正）

**0/33。** 33 个任务全部由执行方自主完成到测试通过，无一次需要人工指出问题、补写代码或返工重做。

### 5.2 自愈循环（执行方自主发现问题 → 自主修复 → 重跑通过）

按方案 9.4 节定义，自主循环属正常执行机制、不计入返工，但它是"提示词留白是否可被自我兜底"的关键信号：

| 任务 | 循环次数 | 问题性质 | 自主修复方式 |
|---|---|---|---|
| T-UI-03 | 1 | 测试编排：两次点击放进同一 `act` 块，首次状态未 flush | 拆成两个独立 `act` 块 |
| T-UI-04 | 1 | 测试查询方式：按钮有 `aria-label`，按可见文本查不到 | 改用 `getByRole('button', { name })` |
| T-UI-05 | 2 | 测试类型断言（`HTMLElement` 无 `disabled`）+ mock 复用同一 Response 触发 `Body is unusable` | 改用 `getAttribute('disabled')`；按 URL 分支返回独立 Response |
| T-CFG-04 | 2 | 环境机制：`target/test-data/` 目录不存在导致上下文加载失败；`src/test/resources` 遮蔽主类路径同名配置 | 放弃 `@SpringBootTest` 方案，改用纯 JUnit（`YamlPropertiesFactoryBean` + `StandardEnvironment`） |
| T-CFG-05 | 1 | 实现路径试错：曾试 `function apiBase()` 便于 stub，后 revert 回 spec 原定的顶层 `const` | 回退到 spec 写法，改用 `vi.resetModules() + await import()` 强制模块重求值 |

**统计**：本轮 27 个任务中 **5 个（18.5%）出现过自愈循环**；第一轮 6 个任务中 4 个（66.7%）出现过。**33 个样本合计 9 个任务（27.3%）经历过自愈循环，全部自主收敛，零人工介入。**

**关键判读**：这 5 个循环的性质高度一致——**4 个是测试编排/测试查询方式问题，1 个是实现路径试错**，没有一个是"业务逻辑写错"或"没推导出隐含规则"。这与第一轮"自主修复 2 处任务说明缺陷"的性质不同（那一轮修的是**任务说明的错**，这一轮修的是**自己测试代码的错**）。两轮合起来说明：当前提示词体系给到的隐含规则显式化，确实把"业务规则漏推理"这类最难兜底的风险压到了 0。

## 七、本轮暴露的"任务说明本身缺陷"（5 处，均被自主修复）

延续第一轮的记录方式——**不是"执行得好不好"，而是"任务说明本身哪里写错了"**：

### 7.1 确定性缺陷（3 处，任务说明给出的断言/预测与仓库实际不符）

1. **T-CFG-01｜技术断言未验证（重演类）**：spec 写 `cd client && npm ci && npm run typecheck`。本仓是 npm workspaces monorepo（`client` 是子 workspace、无独立 `package-lock.json`），`cd client && npm ci` 无法正确安装。执行方自主识别并改为根级 `npm ci && npm run typecheck`，同时如实标注为偏离。
2. **T00201｜技术选型断言错误（第一轮同坑重演）**：spec 首选在 `schema.sql` 写 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS email TEXT`。这**正是第一轮 T00103 已经踩过并记录过的坑**（SQLite JDBC 不支持 `IF NOT EXISTS` 语法）；叠加本仓 `spring.sql.init.mode: always` 使 `schema.sql` **每次启动重放**，裸 `ADD COLUMN` 第二次启动必失败。执行方取 spec 自己的兜底路径（`PRAGMA table_info` 探测 + 条件 `ALTER`，且不落 `schema.sql`）。**结论：第一轮第六节提出的"技术选型可验证性标注"规则（v4）已落地到提示词，但任务说明里同类断言仍然出现——说明该规则还停留在"要求标注"，没有变成"生成时强制核对"的机制。**
3. **T00302｜预计文件与实际不符（新类型）**：spec 预测 `App.tsx`（必须改动）与 `styles.css`（可能改动），实际 `T00301` 已把两者都实现完毕，本任务真正要做的只有补测试。**这是前两轮从未暴露的类型：任务说明在展开时未核对前置任务的真实交付结果**，属跨任务的知识同步缺口。

### 7.2 信息缺失（2 处，实现过程中才暴露）

4. **T-CFG-04｜新机制的环境性约束未预判**：spec 未提示 `target/test-data/` 目录不存在会导致 `sql.init.mode: always` 下的上下文加载失败，也未提示 `src/test/resources/` 会遮蔽主类路径同名配置。执行方两次失败后改用纯 JUnit 规避。

## 九、不能下的结论 / 样本局限

- **不能**据此宣称"执行模型的一次通过率达标（≥80%）"——除第一轮已列的理由外，本轮新增一条：**33 个样本的执行模型归属尚未确认**（第〇.1 节）。若执行模型不是 qwen3.8:27b，本报告只能作为"提示词体系在 33 个新样本上的表现"证据。
- **不能**据此宣称"成本压缩比达标"——**33/33 份报告均未记录生成侧 token/耗时**，Haiku 4.5 基线也未跑。Phase 0 的两个数字里，这个仍是 0 数据。
- **不能**据此宣称"6 个标签全部达标"——`crud`/`config` 与 `business-logic` **两个标签的样本量都还低于门槛**（第三节 3.2），它们的 100% 通过率建立在 8 个和 6 个样本上，置信区间依然很宽。
- **不能**据此把两轮数字直接并成"39 个样本"——实际是 33 个（第〇.2 节）。
- **判定标准仍是"测试通过 + 人工核对"，不是 spec-verifier**；`T-CFG-02` 那类"DoD 无法由测试命令证明"的情形（占位符生效性），本轮靠执行方如实声明边界来处理，说明宽松口径下的风险是**真实存在**的——换成 spec-verifier 严格口径后，通过率有下降可能。
