## 工作流A：补齐成本压缩比数据

> **调整**：不再用Claude做基线对照——改为对照两个更贴近商业方案"多档位路由"框架的档位：**Claude Haiku 4.5**（云端便宜/快速档，代表方案里"32B云"这个中间档位的参照物）与本地 **qwen3.8:27b**。不涉及Claude Sonnet/Opus这类高价档，避免把"压缩比"算得虚高失真。

### A.1 采集口径（先锁定，避免后面数据对不上）

| 维度 | qwen27侧 | Haiku 4.5侧 |
|---|---|---|
| 耗时 | 每任务开始/结束时间戳，人工记录（简单可靠，必采） | Agent工具调用（`model: "haiku"`）自带`duration_ms`，工具返回里直接有（必采） |
| Token量 | **尽力而为**：Ollama服务端（`http://192.168.2.11:11434`）的请求日志/`/api/chat`响应里的`eval_count`/`prompt_eval_count`可查，但Copilot Agent模式下不一定暴露给用户；拿不到精确值就退化为只用耗时做代理指标 | Agent工具调用返回自带`subagent_tokens`，**精确、不需要额外采集**（本对话前面每次Agent调用后都打印过这个数字） |
| $成本 | 视为**~0**（本地推理边际成本，按商业方案"本地近零"的框定处理，不折算电费/硬件摊销——这是本阶段验证的简化处理，跟商业方案口径一致） | Token量 × Claude Haiku 4.5当前定价（按Anthropic官方价目表） |

### A.2 具体操作：6个已完成任务的Haiku基线补齐（成本最低，建议先做这个）

**问题**：这6个任务的代码已经被qwen实现并合并到`main`了，不能直接在当前`main`上让Haiku重做一遍（会跟已有实现冲突，而且"看着现成代码抄"跟"独立实现"不是一回事，数据没有可比性）。

**解决方式**：对每个任务，用`git log`找到该任务PR合并**之前**的那个commit，在一个隔离worktree里checkout到那个commit，喂给Haiku完全相同的任务说明（`qwen27/登录故事-单任务实现清单v3-SpringBoot-PRonly.md`里已经写好的6份，不用重新生成），让它独立实现一遍，记录`<usage>`里的token数与耗时。

已核实的6个"任务开始前"锚点commit（`git log`直接查得，不是推测）：

| 任务 | 该任务PR合并前的commit（Haiku应在此基础上开始） |
|---|---|
| T00101 | `fe2c129`（`fe2c1296bfd5defec438aef05be5c473b2edb226`，即 PR #1 主分支父提交，登录故事启动前的 main 状态；原文"main最初状态"已由此 SHA 固定） |
| T00102 | PR #1合并提交 `0357275` |
| T00103 | PR #2合并提交 `f1d2c3a` |
| T00104 | PR #3合并提交 `d4b62cd` |
| T00105 | PR #4合并提交 `6db9170` |
| T00106 | PR #5合并提交 `60d9625` |

执行步骤（每个任务一次）：
1. `git worktree add <临时路径> <对应锚点commit>` 创建隔离工作区
2. 用`Agent`工具（`model: "haiku"`，`isolation: "worktree"`或手动指定该临时路径）+ 该任务在`登录故事-单任务实现清单v3-SpringBoot-PRonly.md`里的完整任务说明，调用一次Haiku真实实现
3. 记录返回结果里的`subagent_tokens`、`duration_ms`，以及是否一次通过（`mvn test`/`npm run typecheck`跑一遍确认）
4. 清理worktree（`git worktree remove`），不要把Haiku这次的实现推到远程（这是纯粹的数据采集，不是要产出第二套实现）

**产出**：一张6行的表，每行是"任务ID / Haiku token数 / Haiku耗时 / qwen耗时（已从6份交付报告的测试运行时间戳倒推，或需要回头问你当时记没记录）/ 成本比"。

### A.3 后续批次：新样本跑的时候同步采集

工作流B新增的任务，每个任务执行时**从一开始就按A.1的口径记录**（qwen27 + Haiku 4.5两侧同步跑），不要等事后再补——事后补的成本远高于跑的时候顺手记。
