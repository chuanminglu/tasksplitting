## 1. 任务目标（对齐 AC-3 / 验收标准）

验收标准原文：

> 上传非 jpg/png 或 >2MB 时，前端收到明确、可读、与原因对应的失败提示。

DoD 原文：

> - 非 jpg/png → 400 + `UNSUPPORTED_FORMAT`，且 `avatarUrl` 未变；
> - 超过 2MB（合规格式）→ 400 + `FILE_TOO_LARGE`，且 `avatarUrl` 未变；
> - 两类错误码不同，前端可据此给不同文案。

即：当前端选择/拖入一张非 jpg/png 或超过 2MB 的图片时，不能静默失败或弹出无意义的错误，而要给出与具体原因对应的明确提示。核心是**后端在格式/大小不合规时返回 400 与可区分的错误码/文案**，并**不做魔数嗅探、不改动成功路径**。

## 3. 技术选型一致性核对

- **格式校验方式与全局选型一致**：任务书规定「仅依据声明的 `contentType` 判断，不做魔数字节嗅探」，本次用 `file.getContentType()`（小写化）对照白名单 `{image/jpeg, image/png}` 判定，未引入 `MimeTypes` 嗅探库或字节头探测，与项目既有轻量栈（Spring MVC + JdbcTemplate + SQLite）一致。
- **大小校验与全局选型一致**：任务书规定「`getSize() > 2*1024*1024` 时拒绝」，本次用 `long MAX_SIZE_BYTES = 2L*1024*1024` + `file.getSize() > MAX_SIZE_BYTES` 精确实现，边界（恰好 2MB）放行、2MB+1 拒绝。
- **错误响应结构沿用现有约定**：400 响应体为 `{ "error": { "code": "...", "message": "..." } }`，与现有「空文件」校验（`code=EMPTY_FILE`）保持一致的两段式结构，前端可据 `error.code` 区分原因、给不同文案，未引入全局异常处理器或新依赖。
- **仅声明值判定、不校验真实魔数**：符合「不要做魔数字节嗅探」的明确要求（测试用例即以声明的 `contentType` 作为判定输入）。

## 4. 新增测试用例（3 条）

| 用例 | 断言 | 结果 |
|---|---|---|
| `uploadUnsupportedFormatReturns400AndDoesNotPersist` | 非 jpg/png（`image/gif`）→ 400 + `error.code=UNSUPPORTED_FORMAT` + `error.message=仅支持jpg/png格式`；且重新查 `user.avatarUrl` 为 `null`（未变） | 通过 |
| `uploadOversizedFileReturns400AndDoesNotPersist` | 合规 `image/png` 但 2MB+1 字节 → 400 + `error.code=FILE_TOO_LARGE` + `error.message=文件大小不能超过2MB`；且 `avatarUrl` 仍为 `null`（未变） | 通过 |
| `uploadSupportsBoundarySizeExactlyTwoMegaBytes` | 恰好 2MB 的 `image/png` → 200 + `url` 字段存在（边界不越界） | 通过 |

覆盖 DoD 三条：① 非 jpg/png → `UNSUPPORTED_FORMAT` 且 avatarUrl 未变；② 超 2MB 合规格式 → `FILE_TOO_LARGE` 且 avatarUrl 未变；③ 两类错误码不同（`UNSUPPORTED_FORMAT` ≠ `FILE_TOO_LARGE`）。
