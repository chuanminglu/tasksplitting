## 二、单任务标准操作流程（SOP）

每个任务，不论属于哪个阶段，都走同一套12步流程：

```
1. git checkout main && git pull origin main
   ── 确保从最新main出发，这对阶段4a/4b的链式任务尤其重要（后一个任务需要看到前一个任务的真实合并结果）

2. git checkout -b <分支名>
   ── 分支命名：<任务ID小写>-<任务简称拼音或英文缩写>，例如 t-tg-01-todo-empty-title-test、t00201-forgot-password-request

3. 打开新的Copilot Chat（Agent模式，模型qwen3.8:27b），复制对应文档里该任务的完整内容粘贴
   ── 粘贴前，在固定前缀末尾追加"报告写入指令"（见下方"四、交付报告"一节的追加文本），确保Copilot把交付报告写成文件而不只是聊天里回复

4. 等待Copilot执行完成（自主跑测试、自主修复，直到通过或如实说明卡住）

5. 人工核对"完成定义（DoD）"逐条是否真的满足
   ── 打开Copilot写的交付报告文件，对照测试输出核实，不要只信汇报文字

6. 核对交付报告文件是否已按模板生成（见第四节），缺失则要求Copilot补齐或人工补充

7. git add -A

8. git commit -m "<类型>(<任务ID>): <任务名> (<对应AC或说明>)"
   ── 类型用 feat（新功能类）或 test（补测试类）或 chore（配置类），跟各任务文档里已给的commit信息一致

9. git push -u origin <分支名>

10. gh pr create --title "<类型>(<任务ID>): <任务名>" --body "<对DoD的简要说明+关联交付报告路径>"

11. 确认PR满足任务要求
    ── 走查PR diff是否只覆盖本任务范围（对照"预计涉及文件"和"明确不要做的事"）；确认CI（若T-CFG-01已合并生效）跑绿，或至少确认本地测试记录已在交付报告里；确认交付报告文件本身也在这个PR里

12. gh pr merge <分支名> --squash --delete-branch
    然后 git checkout main && git pull origin main
    ── 一条命令合并+删除远程分支；本地切回main并拉取，为下一个任务做准备
```

**第11步"确认PR满足任务要求"没通过怎么办**：回到第3步，在同一个Copilot会话里指出具体问题，让它修正；不要跳过复核直接合并。

## 三、并行执行的额外注意事项

如果决定用多个Copilot会话同时跑阶段1/2/3内部的多个任务（或同时跑4a和4b）：

- 每个并行任务在**第1步**都要各自从当时最新的`main`拉出分支——如果任务A已经合并、任务B还没跑完就已经落后于新`main`，任务B合并前需要`git rebase main`处理冲突（阶段1/2/3的任务大多改动不同文件，冲突概率低；但都改了`App.tsx`的多个`T-UI-*`任务之间冲突概率较高，建议这几个还是串行）
- **阶段4a和4b可以并行**（两条链互不相关），但**同一条链内部不能并行**（T00202不能在T00201合并前开始，因为它需要自查T00201真实交付的代码结构）
- `T-UI-01`～`T-UI-08`全部改`App.tsx`，虽然理论上"任意顺序"，但**实际建议串行执行**，避免多个并行分支同时改同一个文件产生大量合并冲突

## 四、交付报告

### 4.1 在Copilot提示词里追加的指令

每个任务的固定前缀（"你现在处于一次任务执行能力测试中..."那一段）末尾，额外追加这一段再粘贴：

```
完成上述所有工作后，把"交付要求"里要求汇报的内容，按下面的结构整理成一份完整的Markdown文档，用你的文件写入能力保存到 docs/任务拆解/补齐计划/交付报告/<任务ID>-<任务简称>-交付报告.md（文件名里的任务简称用几个字概括任务名，不含空格，如T-TG-01-Todo空标题校验补测试-交付报告.md）：

# <任务ID> 交付报告 — <任务名>

> 任务编号：<任务ID>
> 验收标准：<对应AC或"无新增AC，验证既有行为">
> 验收模式：PR-only
> 交付日期：<今天日期>

## 一、任务概述
（一两句话说明做了什么）

## 二、实际改动的文件（与"预计涉及文件"逐项核对）
（表格：预计文件 | 状态 | 说明；然后"可能改动"清单最终有没有改；如有计划外新增文件，单独列出并说明理由）

## 三、实际技术选型是否与说明一致
（逐条核对"技术选型"章节列出的每个决策点，实际是否照做；如有偏离，说明原因）

## 四、新增的测试用例
（表格或列表：测试位置 | 用例名 | 覆盖的DoD点）

## 五、测试运行结果（原样节选）
（把mvn test / npm run typecheck / npx vitest run 的真实输出片段贴进来，不要复述"全部通过"这种转述，要有真实命令输出）

## 六、是否有偏离范围的地方
（对照"明确不要做的事"逐条确认；如有偏离必须说明原因）

## 七、交付物与后续事项
（分支名、PR链接留空由人工在合并后补充；后续任务可参考的接口/约定，如适用）
```

所有27个任务的交付报告统一存到 `docs/任务拆解/补齐计划/交付报告/` 目录下（新建），不要和`qwen27/`目录下登录故事的6份报告混在一起——按批次分开存放，方便后续按批次做benchmark评估。
