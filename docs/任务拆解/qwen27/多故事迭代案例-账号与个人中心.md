## 如何生成单任务实现简报

以上任务清单是规划阶段的路线图，颗粒度只到"任务名+验收标准要点"。某条具体任务真正要派发给执行者前，使用`单任务实现简报-subagent提示词.md`，把这条任务的完整条目 + 其所属故事的模式判断/flag上下文 + 当下最新的REPO_PATH自查结果喂进去，现场生成一份完整自包含简报再派发。跨故事有依赖的任务（如T00201、T00301），必须等依赖的前序任务（T00101）实际合并后，再生成简报。

## 案例要点小结

1. **两阶段真的分开了颗粒度**：第一阶段总览里T00201的"预计涉及文件"只有3个分类级`[ASSUME]`条目；第二阶段结合T00101的真实交付结果，展开成7条具体路径，且全部标`[INFER]`（因为没有真实REPO_PATH核实，只能基于材料4推算，不能升级成`[FACT]`）——这正是证据分级标注要防止的事：不能因为"依赖任务已交付、材料更充分了"就把置信度偷偷拔高到`[FACT]`。
2. **前序任务的偏离被老实带到了下一个任务**：T00101额外加的`email`字段，被T00201的"背景"部分明确引用并标`[FACT]`（因为这是材料4原文记载的既成事实），而不是被忽略或重新臆测一遍。
3. **跨故事依赖在两个阶段都没丢**：总览阶段标了"T00201依赖T00101"，单任务展开阶段的"明确不要做的事"里重申了"若依赖任务实际未合并，暂停并报告"——依赖信息没有在传递过程中弱化成一句空话。
4. **没有REPO_PATH时，整个链条都诚实地打了折扣**：总览的跨故事排查、单任务的文件预估，全篇没有一处把`[INFER]`/`[ASSUME]`包装成`[FACT]`，且反复出现"建议有REPO_PATH后重新校准"——这是三闸口"验证闸退化边界"那条原则在多故事场景下的具体体现。
