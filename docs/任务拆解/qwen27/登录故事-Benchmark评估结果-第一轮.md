## 四、两个真实发现：任务说明本身的缺陷，被qwen自主修复

这是本轮最值得记录的部分——**不是"qwen做得好不好"，而是"Claude写的任务说明本身有两处真实错误，qwen在没有人工介入的情况下独立诊断并修复了"**：

1. **T00103**：技术选型章节断言了一个未经验证的SQL语法兼容性（`ADD COLUMN IF NOT EXISTS`），实际不支持。这是"写技术选型时把'版本号听起来应该支持'当成'已验证支持'"的疏漏。
2. **T00106**：规划schema管理机制（T00101）时，没有审计代码库里所有依赖旧机制（Prisma dev.db）的既有表，只顾及了新增的User/Session/LoginEvent，漏了本来就存在的Todo表。这是"引入新基础设施时未做旧结构的覆盖盘点"的疏漏。

两处都被qwen在同一任务内自主发现、自主修复、自主验证通过，**过程零人工介入**——这本身是对qwen执行能力的强烈正面信号（任务说明有错都能自己纠正，不是死板照抄），但也说明当前的提示词在"技术选型断言的可验证性"和"新基础设施的覆盖完整性"这两点上还有改进空间。第六节给出具体改动。

## 五、样本局限性——不能下的结论

- **不能**据此宣称"qwen3.8:27b一次通过率达标（≥80%）"——6个样本，商业方案要求50个/技术栈才能作为Phase 0依据，置信区间太宽，一两个任务的偶然失败就会让比例大幅波动
- **不能**据此宣称"成本压缩比达标"——本轮完全没有可比的token/耗时数据，这一指标本轮事实上是空白
- **不能**据此宣称"novel-design/refactor类任务都该下沉到本地模型"——只各测了1个样本，且都是同一个故事内前后连贯的任务（qwen在T00101打下的良好基础上，后续任务天然更容易成功），不能代表这两个标签下所有任务的普遍难度
- **判定标准是"测试通过+人工核对"而非spec-verifier**，比商业方案真正要求的口径更宽松，之后接入spec-verifier重跑同一批样本时，通过率可能会下降

## 六、给两份提示词的改动建议

基于第四节两个真实发现，`单任务实现-subagent提示词.md` 需要补两条规则（已实施，见文件v4）：

1. **新基础设施覆盖完整性规则**：当任务引入一套新机制（如schema管理）取代或兼容旧机制时，"预计涉及文件"自查阶段必须盘点代码库里所有依赖旧机制的既有结构，不能只覆盖本任务新增的部分——这条直接对应T00106踩的坑。
2. **技术选型的可验证性标注**：技术选型里涉及具体工具/库/语法层面的断言（如"某驱动版本支持某SQL语法"），如果未经实际验证，不能写成确定性陈述，应标`[ASSUME]`并显式授权执行者"若实测不支持，可替换为语义等价的实现方式，不算偏离本选型决策"——这条对应T00103踩的坑，虽然qwen这次自己处理得很好，但把这个授权写明确，能降低对能力更弱的模型造成卡壳的风险。

`迭代任务分解-subagent提示词.md` 本轮**不需要改动**——两个发现都发生在单任务展开层面（技术选型细节、schema覆盖盘点），不涉及故事拆分粒度或跨故事排查逻辑，不属于这份提示词的职责范围。
