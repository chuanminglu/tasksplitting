# qwen本地模型任务拆解 Benchmark 验证方案

> 版本：v1.0 | 2026-09-21
> 目的：回答 `VueReact+Java专用Harness商业方案.md` Phase 0 提出的两个前置问题——
> 当前的任务拆解粒度/提示词体系，能否让 qwen3.8:27b 这样的本地模型独立承接约80%的开发任务？
> 验证结论直接决定商业方案是否具备继续投入（Phase 1）的资格。

---

## 一、背景与必须先说清楚的一个前提

### 1.1 商业方案的硬性前提（Phase 0 两个数字）

`VueReact+Java专用Harness商业方案.md` 第 6.2 节明确写道，这两个数字不达标，方案不成立：

| 数字 | 定义 | 达标线 | 回炉线 |
|---|---|---|---|
| **一次通过率** | Vue组件+Spring接口各抽50个真实任务，看spec-verifier一次绿的比例 | ≥80% → 可推 | <60% → SDD/拆解策略需要改 |
| **成本压缩比** | 同批任务分别用"纯70B"和"17B+校验+20%升级70B"跑，算token账单比 | ≥1:5 且缺陷密度不显著上升 → 销售故事立得住 | 未达标 → 方案的经济性不成立 |

本方案就是为了跑出这两个数字设计的，同时补充了更细颗粒度的归因指标（见第三节），用于反哺提示词迭代。

### 1.2 关键前提：现有"成功案例"不能当作 qwen 的证据

`登录故事-切片任务简报-5切片完整交付报告.md` 里"5个切片全部一次通过、23/23测试、0返工"的数据，**执行方是通过 `Agent` 工具调用的 subagent，在当前环境里等同于 Claude 本身执行，不是 qwen3.8:27b**。这份报告只能作为**对照组（上限基准）**使用，不能作为"qwen已验证可用"的依据。本方案第一步就是要把这个空白补上。

### 1.3 模型标识必须先锁定

"qwen3.8:27b" 不是标准 Ollama/vLLM 模型 tag 命名格式，执行本方案前必须先确认并记录以下信息，作为benchmark元数据固定下来，否则结果不可复现、不可对比：

- 具体模型名与版本（如 `qwen2.5-coder:32b`、`qwen3:30b-a3b` 等，以实际部署为准）
- 量化精度（如 Q4_K_M / Q8_0 / FP16）
- 推理参数（temperature、top_p、max_tokens、context window）
- 部署方式与硬件（本地 Ollama / vLLM，GPU型号与显存）

**这四项一旦跑之前不锁定，后续任何"通过率"数字都无法解释是模型能力问题还是配置问题。**

## 二、验证目标与范围

### 2.1 要回答的核心问题

1. 用当前 `docs/任务拆解/prompts/` 下的提示词体系拆出来的任务，qwen3.8:27b 独立执行的**一次通过率**能到多少？按任务类型（crud/business-logic/test-generation）分别是多少？
2. 未通过的任务，问题出在**任务拆解/提示词设计**，还是**模型能力本身**？（这一点决定了"改prompt能不能救回来"还是"这类任务本来就该路由到大模型"）
3. 在保证质量不塌陷（缺陷密度不显著上升）的前提下，qwen方案相对纯大模型方案的**成本压缩比**能到多少？
4. 当前"预计涉及文件""技术选型留白""隐含业务规则"这几处设计，对qwen的通过率影响有多大（用于反哺提示词修改优先级）？

### 2.2 本轮不覆盖的范围（明确排除，避免样本/时间失控）

- 不覆盖架构级重构、算法类任务（商业方案里这类任务本来就路由给70B+，不是qwen要承接的范围）
- 不做多模型横向对比（如qwen vs DeepSeek vs 其他17B级模型），本轮只验证qwen3.8:27b一个模型
- 不在本轮做生产环境真实发布验证，止步于"spec-verifier/测试门禁通过"这一层

## 三、样本集设计

### 3.1 样本来源优先级

1. **优先**：从真实 Vue/React + Java Spring 项目的历史任务里抽样（已完成或待完成均可，已完成的可以"回放"——重新让qwen做一遍，再和人工原始实现对比）。真实项目才能测出"预计涉及文件是否准"这类只有真实代码库才暴露的问题。
2. **补充**：登录故事6个任务（`docs/任务拆解/prompts/登录故事-任务清单示例.md`）作为**回归基准**，因为已有Claude执行的高质量对照结果（5切片报告），可以直接复用对照，不需要重新构造。
3. **不建议**：全部用新编造的demo任务——demo没有真实代码库，测不出"文件命中率"这个关键维度，且容易因为设计者对答案心中有数而低估任务的实际模糊度。

### 3.2 样本量与分层

按商业方案的路由标签分层抽样，每层不少于10个真实任务，总量建议**不少于40个**（数量太少时80%这个比例的置信区间会很宽，几个任务的偶然失败就能让结果从"达标"变"不达标"）：

| 路由标签 | 定义 | 建议样本量 | 典型例子 |
|---|---|---|---|
| `crud` / `config` | 增删改查、配置项、简单UI | ≥12 | 登录故事任务1（最小登录闭环）、账户资料编辑接口 |
| `business-logic` | 多分支/状态机/中等复杂业务规则 | ≥12 | 登录故事任务3（锁定规则）、任务4（会话差异化） |
| `test-generation` | 只补测试，不改业务逻辑 | ≥8 | 为已有接口补集成测试 |
| `simple-ui` | 纯前端展示/交互，无复杂状态 | ≥8 | 登录故事任务2的前端错误文案展示部分 |

### 3.3 每个样本必须具备的最小信息

- 已经过 `迭代任务分解-subagent提示词.md` + `单任务实现简报-subagent提示词.md` 两级展开，格式与登录故事示例一致
- 有明确的验收标准（AC），可转化为自动化测试断言
- 已标注路由标签（若原任务清单未标注，抽样时人工补标，不能凭感觉分组）
- 记录该任务在真实项目中人工实现耗时/改动文件数（如有），作为后续对比基线

## 四、评测维度与指标定义

### 4.1 核心指标（直接对应商业方案要的两个数字）

| 指标 | 计算方式 | 数据来源 |
|---|---|---|
| **一次通过率** | 不做人工修改、不重试，simple地跑spec-verifier/测试门禁，通过记1否则记0；总通过数/总任务数 | spec-verifier CLI 或等价测试命令输出 |
| **分标签通过率** | 按 3.2 的四个标签分别计算通过率 | 同上，按标签分组统计 |
| **成本压缩比** | 同批任务分别用当前默认大模型（Claude/70B）与qwen方案（含校验+失败升级）跑，比较token消耗或时长 | 模型API/本地推理的token计数或wall-clock时间 |

### 4.2 归因与诊断指标（用于反哺提示词迭代，比总分更有信息量）

| 指标 | 计算方式 | 用途 |
|---|---|---|
| **文件命中率** | 预计涉及文件 vs 实际改动文件，逐条核对，命中数/预计数 | 判断"预计涉及文件"这个兜底机制对小模型是否失效；参照5切片报告100%作为上限对照 |
| **返工率** | 需要二次修复才能过门禁的任务占比；记录每个任务经过几轮才过 | 返工轮次分布可以看出"改一次就能救"还是"结构性不会做" |
| **范围蔓延率** | diff是否触碰了"明确不要做的事"里列出的禁止范围 | 验证任务边界设计对小模型是否仍然有效 |
| **升级率** | 触发"qwen连续3轮未过→自动升级大模型"规则的任务占比 | 这个数字比总通过率更贴近商业结论——它直接等于"实际能留在qwen上的任务比例" |
| **失败归因分类** | 见4.3 | 决定改prompt还是改路由策略 |

### 4.3 失败归因分类标准（人工标注，每个未一次通过的任务必须归入且只能归入一类主因）

1. **预计文件猜错**：模型改动的文件与真实需要改动的文件不一致，导致改动位置错误或遗漏
2. **技术选型走偏**：模型在prompt留白的选型点（如存储方式、凭证形式）上选了不符合项目现有约定的方案
3. **业务规则漏推理**：模型没有推导出AC隐含的分支规则（如"锁定被成功登录打断则清零"这类未直写的规则）
4. **代码正确性问题**：以上都不是，纯粹是模型写的代码本身有bug（语法错误、逻辑错误、边界条件处理错误）
5. **测试覆盖不足**：功能实现对，但没写测试或测试断言不到位，门禁因此不过

归因分布决定优先级：如果①②③占比高，说明问题在提示词设计，优先改prompt；如果④占比高，说明是模型能力天花板问题，该任务类型可能本来就不该分给qwen，需要调整路由阈值而不是死磕prompt。

## 五、执行流程

### Step 0：环境与元数据锁定
- 确认并记录 1.3 节的四项模型元数据
- 确认 spec-verifier（或等价门禁工具）在本地可用，输出结果可结构化解析（通过/不通过 + 违规明细）

### Step 1：基线跑（对照组）
- 同一批样本任务，用当前默认大模型（Claude 或方案里的70B档）跑一遍，走相同的提示词模板
- 记录一次通过率、文件命中率、耗时/token作为**上限基准**
- 登录故事6任务可直接复用已有的5切片报告数据，不需要重跑

### Step 2：qwen跑（实验组）
- 同一批任务原样喂给qwen3.8:27b，**prompt模板与Step 1完全一致**，不做人工干预、不做重试
- 每个任务独立会话执行（避免上下文污染），完整记录：输出内容、门禁结果、实际改动文件、执行耗时/token
- 触发"连续3轮未过"的任务，按商业方案规则升级到大模型，记录升级发生的节点（这次升级本身不算在"qwen一次通过率"里，但要计入"升级率"）

### Step 3：失败样本归因
- 对Step 2里所有未一次通过的任务，按4.3标准人工标注主因
- 每条归因附简短说明（如"任务3：模型未实现锁定被成功登录打断清零的分支，归类为③业务规则漏推理"）

### Step 4：汇总与结论
- 汇总4.1的核心指标（总通过率、分标签通过率、成本压缩比）
- 汇总4.2的诊断指标与4.3的归因分布
- 对照商业方案阈值给出明确结论：达标可推 / 部分达标需针对性改prompt再测一轮 / 不达标需重新评估该模型是否适配

### Step 5：闭环——回改提示词，二次验证
- 根据归因分布，优先修复占比最高的问题类型（预计已知的四个方向见下方"六、已规划的提示词改动"）
- 只对**归因为①②③（提示词可解的问题）**的任务子集做二次验证，不需要重跑整个样本集
- 二次验证通过率提升幅度，作为"提示词改动是否有效"的直接证据

## 六、已规划的提示词改动（待Step 3归因结果验证优先级后再实施）

以下四点已在方案讨论中识别，作为Step 5的候选改动清单，具体是否落地及优先级以本次benchmark的归因分布为准：

1. `单任务实现简报-subagent提示词.md` 新增"技术选型收敛"强制字段，避免把选型开放给执行者
2. "预计涉及文件"拆分为"必须改动"与"可能改动（依赖当场决策）"两档
3. 业务隐含推理规则显式化，在"你要做什么"里强制逐条列出从AC推导出的隐含分支
4. `迭代任务分解-subagent提示词.md` 的任务条目补充"路由建议标签"字段，便于benchmark自动分组统计

## 七、数据记录模板

建议用一张表跟踪每个样本任务的完整生命周期，字段如下（可落地为CSV/表格工具）：

| 字段 | 说明 |
|---|---|
| 任务ID | 对齐单任务简报的任务编号 |
| 路由标签 | crud/business-logic/test-generation/simple-ui |
| 来源 | 真实项目路径 或 登录故事回归基准 |
| 基线结果（Claude） | 通过/不通过、文件命中率、耗时/token |
| qwen结果 | 通过/不通过、文件命中率、耗时/token、经过轮次 |
| 是否升级 | 是/否，若是记录升级节点（第几轮） |
| 失败归因 | 归入4.3五类中的哪一类（未失败则空） |
| 归因说明 | 一句话描述具体问题 |
| 备注 | 其他异常情况 |

## 八、已知局限与风险

- **样本代表性**：40个任务的分层抽样能给出方向性结论，但商业方案要求的"50个"级别的精确阈值验证，建议在方向确认后再补足样本量到各标签50个
- **门禁工具本身的成熟度**：若spec-verifier规则库覆盖不全，"一次通过率"可能被门禁的漏检/误报干扰，需要在Step 0确认门禁工具本身在基线组（Claude）上的表现是否符合预期，排除工具问题再归因到模型
- **真实项目样本获取成本**：若暂时拿不到足够的真实历史任务，可先用登录故事+账号个人中心案例（`prompts/多故事迭代案例-账号与个人中心.md`）的任务清单展开出简报作为过渡样本，但要在结论里明确标注"部分样本非真实代码库，文件命中率维度结果需降权参考"
