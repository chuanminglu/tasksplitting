# qwen本地模型任务拆解 Benchmark 验证方案

> 版本：v1.1 | 2026-09-21
> 目的：回答 `VueReact+Java专用Harness商业方案.md` Phase 0 提出的两个前置问题——
> 当前的任务拆解粒度/提示词体系，能否让 qwen3.8:27b 这样的本地模型独立承接约80%的开发任务？
> 验证结论直接决定商业方案是否具备继续投入（Phase 1）的资格。
> **v1.1变更说明**：① 本地验证项目（`tasksplitting`）后端已从 Node.js+Express+Prisma 实际迁移为 Spring Boot 3.4.4（Java 17，JdbcTemplate手写SQL，无ORM），本文档涉及具体技术栈示例的部分同步更新，与 `登录故事-任务清单v3-SpringBoot.md` / `登录故事-单任务实现清单v3-SpringBoot-PRonly.md` 对齐；② **本阶段暂不接入spec-verifier门禁**，"一次通过率"改用"项目自身测试命令通过 + 人工核对DoD逐条断言"作为临时判定标准，原因是spec-verifier尚未针对Spring Boot技术栈配置规则库，强行接入会把"工具没配好"和"模型能力不够"两种失败原因混在一起，无法干净归因；待spec-verifier规则库就绪后再升级判定标准，并需重新评估早期数据与新标准的可比性。

## 一、背景与必须先说清楚的一个前提

### 1.1 商业方案的硬性前提（Phase 0 两个数字）

`VueReact+Java专用Harness商业方案.md` 第 6.2 节明确写道，这两个数字不达标，方案不成立：

| 数字                 | 定义                                                            | 达标线                                       | 回炉线                       |
| -------------------- | --------------------------------------------------------------- | -------------------------------------------- | ---------------------------- |
| **一次通过率** | Vue组件+Spring接口各抽50个真实任务，看spec-verifier一次绿的比例（**本阶段暂用"项目自身测试命令通过+人工核对DoD"替代**，见v1.1变更说明） | ≥80% → 可推                                | <60% → SDD/拆解策略需要改   |
| **成本压缩比** | 同批任务分别用"纯70B"和"17B+校验+20%升级70B"跑，算token账单比   | ≥1:5 且缺陷密度不显著上升 → 销售故事立得住 | 未达标 → 方案的经济性不成立 |

本方案就是为了跑出这两个数字设计的，同时补充了更细颗粒度的归因指标（见第三节），用于反哺提示词迭代。

### 1.2 关键前提：现有"成功案例"不能当作 qwen 的证据

`登录故事-切片任务简报-5切片完整交付报告.md` 里"5个切片全部一次通过、23/23测试、0返工"的数据，**执行方是通过 `Agent` 工具调用的 subagent，在当前环境里等同于 Claude 本身执行，不是 qwen3.8:27b**。这份报告只能作为**对照组（上限基准）**使用，不能作为"qwen已验证可用"的依据。本方案第一步就是要把这个空白补上。

**另需注意**：该5切片报告的实现基于当时的 Node.js+Express+Prisma 技术栈，本地验证项目 `tasksplitting` 的后端此后已实际迁移为 Spring Boot 3.4.4（Java 17，JdbcTemplate手写SQL，无ORM），因此该报告只能作为"Claude执行、非qwen"这一结论的证据，其文件路径/技术细节已不代表当前代码库状态，不能作为Step 1基线跑的直接复用素材——Step 1需要针对当前Spring Boot代码库重新跑一次基线（见Step 1更新说明）。

### 1.3 模型标识（已通过 Ollama API 现场核实，2026-09-21）

部署地址 `http://192.168.2.11:11434/`（局域网 Ollama），通过 `/api/tags` 与 `/api/show` 直接查询到的真实数据如下，作为benchmark元数据固定记录：

| 项目          | 值                                                                                 |
| ------------- | ---------------------------------------------------------------------------------- |
| 模型 tag      | `qwen3.8:27b`（本地自定义tag，非官方标准命名）                                   |
| 底层家族      | `qwen35`（即 Qwen3.5 系列），parent_model 为 `qwen3.8:27b-q4_K_M`              |
| 参数量        | 27.3B（27,320,697,856）                                                            |
| 量化精度      | Q4_K_M                                                                             |
| 上下文窗口    | 262144 tokens（qwen35.context_length）                                             |
| embedding维度 | 5120                                                                               |
| 能力标签      | completion / tools / thinking / vision                                             |
| 默认推理参数  | temperature=1, top_p=0.95, top_k=20, repeat_penalty=1, presence_penalty=0, min_p=0 |
| 部署方式      | Ollama，局域网部署，地址 `http://192.168.2.11:11434/`                            |

**两处需要在跑benchmark前明确决策的地方**：

1. **家族是 Qwen3.5 通用模型，不是 Qwen3-Coder**：商业方案 `VueReact+Java专用Harness商业方案.md` 第1.1节给出的"HumanEval 85-92%"参考数据是针对 **Qwen3-Coder** 14B/32B 这条代码专精线的，`qwen3.8:27b` 实际是 `qwen35` 家族的通用27B模型（支持vision/thinking，说明是多模态通用检查点而非代码专精版本）。这意味着商业方案里引用的HumanEval参考分数**不能直接套用到这个具体模型上**，需要在benchmark结论里明确区分"方案假设的模型"和"实际测试的模型"，避免后续汇报时张冠李戴。
2. **默认 temperature=1 偏高，不建议直接用于benchmark**：代码生成类任务通常需要低随机性以保证可复现和稳定性，多数编码benchmark（如HumanEval/SWE-bench）惯例用 temperature 0~0.3。建议正式跑Step 1/Step 2前，将推理参数显式覆盖为一组**固定的低温配置**（如 temperature=0.2, top_p=0.9），并在Step 0记录实际使用的参数——继续用默认temperature=1会引入额外的运行间方差，导致"一次通过率"结果不稳定、跑两次结果对不上。

**执行前必须做的动作**：在 Step 0 正式锁定本次benchmark实际使用的推理参数（是否覆盖默认temperature）、context window 是否需要限制（262144虽大，但受限于实际显存/速度，建议按真实任务prompt长度设定一个更小的实用值并记录），一并写入下方"数据记录模板"的元数据部分。

## 二、验证目标与范围

### 2.1 要回答的核心问题

1. 用当前 `docs/任务拆解/prompts/` 下的提示词体系拆出来的任务，qwen3.8:27b 独立执行的**一次通过率**能到多少？按任务类型（crud/business-logic/test-generation）分别是多少？
2. 未通过的任务，问题出在**任务拆解/提示词设计**，还是**模型能力本身**？（这一点决定了"改prompt能不能救回来"还是"这类任务本来就该路由到大模型"）
3. 在保证质量不塌陷（缺陷密度不显著上升）的前提下，qwen方案相对纯大模型方案的**成本压缩比**能到多少？
4. 当前"预计涉及文件""技术选型留白""隐含业务规则"这几处设计，对qwen的通过率影响有多大（用于反哺提示词修改优先级）？

### 2.2 本轮不覆盖的范围（明确排除，避免样本/时间失控）

- 不覆盖架构级重构、算法类任务（商业方案里这类任务本来就路由给70B+，不是qwen要承接的范围）
- 不做多模型横向对比（如qwen vs DeepSeek vs 其他17B级模型），本轮只验证qwen3.8:27b一个模型
- 不在本轮做生产环境真实发布验证，止步于"项目自身测试命令通过（`mvn test`/`npm run typecheck`等）+ 人工核对DoD逐条断言"这一层；不在本轮接入spec-verifier（尚未针对Spring Boot技术栈配置规则库）

## 三、样本集设计

### 3.1 样本来源优先级

1. **优先**：从真实 Vue/React + Java Spring 项目的历史任务里抽样（已完成或待完成均可，已完成的可以"回放"——重新让qwen做一遍，再和人工原始实现对比）。真实项目才能测出"预计涉及文件是否准"这类只有真实代码库才暴露的问题。
2. **补充**：登录故事6个任务，以 `docs/任务拆解/prompts/登录故事-单任务实现清单v3-SpringBoot-PRonly.md`（Spring Boot技术栈，真实自查`tasksplitting`本地仓库生成，CI/CD=PR-only）为准作为**回归基准**——v1版`登录故事-任务清单示例.md`与5切片报告均基于已废弃的Node.js+Express+Prisma技术栈，技术细节（文件路径/依赖库）已不匹配当前代码库，只能作为方法论演进的历史参考，不能直接拿来跑Step 1/Step 2；v3版才是当前可直接使用的基线素材。

> 引用登录故事v1/v2/v3三个版本时要分清各自定位：v1（`登录故事-任务清单示例.md`）无REPO_PATH、纯`[ASSUME]`推测、Node技术栈；v2（`登录故事-任务清单v2-真实仓库自查.md`）有真实自查但仍是Node技术栈；v3（本节引用的两份文档）是Spring Boot迁移后的真实自查结果，是当前唯一与代码库现状一致的版本。
3. **不建议**：全部用新编造的demo任务——demo没有真实代码库，测不出"文件命中率"这个关键维度，且容易因为设计者对答案心中有数而低估任务的实际模糊度。

### 3.2 样本量与分层

按商业方案的路由标签分层抽样，每层不少于10个真实任务，总量建议**不少于40个**（数量太少时80%这个比例的置信区间会很宽，几个任务的偶然失败就能让结果从"达标"变"不达标"）：

| 路由标签              | 定义                           | 建议样本量 | 典型例子                                        |
| --------------------- | ------------------------------ | ---------- | ----------------------------------------------- |
| `crud` / `config` | 增删改查、配置项、简单UI       | ≥12       | 登录故事任务1（最小登录闭环）、账户资料编辑接口 |
| `business-logic`    | 多分支/状态机/中等复杂业务规则 | ≥12       | 登录故事任务3（锁定规则）、任务4（会话差异化）  |
| `test-generation`   | 只补测试，不改业务逻辑         | ≥8        | 为已有接口补集成测试                            |
| `simple-ui`         | 纯前端展示/交互，无复杂状态    | ≥8        | 登录故事任务2的前端错误文案展示部分             |

### 3.3 每个样本必须具备的最小信息

- 已经过 `迭代任务分解-subagent提示词.md` + `单任务实现-subagent提示词.md` 两级展开，格式与登录故事示例一致
- 有明确的验收标准（AC），可转化为自动化测试断言
- 已标注路由标签（若原任务清单未标注，抽样时人工补标，不能凭感觉分组）
- 记录该任务在真实项目中人工实现耗时/改动文件数（如有），作为后续对比基线

## 四、评测维度与指标定义

### 4.1 核心指标（直接对应商业方案要的两个数字）

| 指标                   | 计算方式                                                                                       | 数据来源                                    |
| ---------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------- |
| **一次通过率**   | 不做人工修改、不重试，跑项目自身测试命令（`mvn test`/`npm run typecheck`等，视任务涉及server/client而定）+ 人工逐条核对DoD断言，全部满足记1否则记0；总通过数/总任务数（**本阶段暂不用spec-verifier**，见v1.1变更说明）      | 项目测试命令输出 + 人工DoD核对记录        |
| **分标签通过率** | 按 3.2 的四个标签分别计算通过率                                                                | 同上，按标签分组统计                        |
| **成本压缩比**   | 同批任务分别用当前默认大模型（Claude/70B）与qwen方案（含校验+失败升级）跑，比较token消耗或时长 | 模型API/本地推理的token计数或wall-clock时间 |

### 4.2 归因与诊断指标（用于反哺提示词迭代，比总分更有信息量）

| 指标                   | 计算方式                                                   | 用途                                                                          |
| ---------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **文件命中率**   | 预计涉及文件 vs 实际改动文件，逐条核对，命中数/预计数      | 判断"预计涉及文件"这个兜底机制对小模型是否失效；5切片报告的100%是Node.js+Prisma技术栈下的历史数字，仅作方法论层面的参照（"精心自查后命中率能到多高"），不作为Spring Boot技术栈下的数值基准——Spring Boot基线需要靠Step 1重新跑出 |
| **返工率**       | 需要二次修复才能过门禁的任务占比；记录每个任务经过几轮才过 | 返工轮次分布可以看出"改一次就能救"还是"结构性不会做"                          |
| **范围蔓延率**   | diff是否触碰了"明确不要做的事"里列出的禁止范围             | 验证任务边界设计对小模型是否仍然有效                                          |
| **升级率**       | 触发"qwen连续3轮未过→自动升级大模型"规则的任务占比        | 这个数字比总通过率更贴近商业结论——它直接等于"实际能留在qwen上的任务比例"    |
| **失败归因分类** | 见4.3                                                      | 决定改prompt还是改路由策略                                                    |

### 4.3 失败归因分类标准（人工标注，每个未一次通过的任务必须归入且只能归入一类主因）

1. **预计文件猜错**：模型改动的文件与真实需要改动的文件不一致，导致改动位置错误或遗漏
2. **技术选型走偏**：模型在prompt留白的选型点（如存储方式、凭证形式）上选了不符合项目现有约定的方案
3. **业务规则漏推理**：模型没有推导出AC隐含的分支规则（如"锁定被成功登录打断则清零"这类未直写的规则）
4. **代码正确性问题**：以上都不是，纯粹是模型写的代码本身有bug（语法错误、逻辑错误、边界条件处理错误）
5. **测试覆盖不足**：功能实现对，但没写测试或测试断言不到位，门禁因此不过

归因分布决定优先级：如果①②③占比高，说明问题在提示词设计，优先改prompt；如果④占比高，说明是模型能力天花板问题，该任务类型可能本来就不该分给qwen，需要调整路由阈值而不是死磕prompt。

## 五、执行流程

### Step 0：环境与元数据锁定

- 模型基础信息已通过Ollama API核实并记录于1.3节（tag/家族/量化/上下文窗口/部署地址）
- **待决策并记录**：本次benchmark实际使用的推理参数（是否将temperature从默认1下调至0.2左右）、实际使用的context window上限——决策结果写入下方"数据记录模板"的元数据部分，作为本轮所有任务的统一配置
- **本阶段不接入spec-verifier**：确认项目自身测试命令可用（`server`目录`mvn test`、`client`目录`npm run typecheck`），输出可读（通过/失败 + 报错信息）即可；门禁判定标准降级为"测试命令通过 + 人工逐条核对DoD"，这条临时标准需要写进数据记录模板的元数据部分，避免后续对比时把不同判定标准的数据混为一谈

### Step 1：基线跑（对照组）

- 同一批样本任务，用当前默认大模型（Claude 或方案里的70B档）跑一遍，走相同的提示词模板
- 记录一次通过率、文件命中率、耗时/token作为**上限基准**
- **登录故事6任务需要针对当前Spring Boot代码库重新跑一次基线**，不能复用旧的5切片报告（该报告基于已废弃的Node.js+Express+Prisma技术栈，见1.2节说明）；可直接使用 `登录故事-单任务实现清单v3-SpringBoot-PRonly.md` 里已经生成好的6份任务说明作为输入

### Step 2：qwen跑（实验组）

- 同一批任务原样喂给qwen3.8:27b，**prompt模板与Step 1完全一致**，不做人工干预、不做重试
- 每个任务独立会话执行（避免上下文污染），完整记录：输出内容、门禁结果、实际改动文件、执行耗时/token
- 触发"连续3轮未过"的任务，按商业方案规则升级到大模型，记录升级发生的节点（这次升级本身不算在"qwen一次通过率"里，但要计入"升级率"）

### Step 3：失败样本归因

- 对Step 2里所有未一次通过的任务，按4.3标准人工标注主因
- 每条归因附简短说明（如"任务3：模型未实现锁定被成功登录打断清零的分支，归类为③业务规则漏推理"）

### Step 4：汇总与结论

- 汇总4.1的核心指标（总通过率、分标签通过率、成本压缩比）
- 汇总4.2的诊断指标与4.3的归因分布
- 对照商业方案阈值给出明确结论：达标可推 / 部分达标需针对性改prompt再测一轮 / 不达标需重新评估该模型是否适配

### Step 5：闭环——二次验证已落地的提示词改动，视归因结果决定是否继续迭代

> 与最初设计有一处调整：下方四点改动**已提前落地到提示词文件本身**（未等Step 3归因数据出来再决定），原因是这四点在方案讨论阶段已有足够把握判断是通用性收益（收窄小模型的开放决策面），不依赖具体归因分布也值得做。Step 5 的任务因此从"决定改不改、改哪个"变成"验证已落地的改动是否真的提升了通过率"——即Step 2用新版提示词跑出来的结果，本身已经是改动后的数据；如果后续归因显示仍有同类问题（如技术选型走偏），再回头看是否需要更细的补丁。

- 对照Step 3的失败归因分布，重点看①②③三类问题（提示词可解的问题）在v2版提示词下是否已经显著下降
- 若某类问题占比仍然偏高，说明当前落地的改法还不够，需要针对该类问题再补一版细化规则，重新走一轮Step 2验证子集（不需要重跑整个样本集）
- 若④（代码正确性）占比高，说明是模型能力天花板问题，提示词改动帮不上忙，需要调整路由阈值而不是继续改prompt

## 六、已落地的提示词改动（v2，2026-09-21落地）

以下五点已在方案讨论中识别并**直接落地**到提示词文件（不再是"候选清单"），作为Step 2起benchmark实际使用的版本：

## 八、已知局限与风险

- **样本代表性**：40个任务的分层抽样能给出方向性结论，但商业方案要求的"50个"级别的精确阈值验证，建议在方向确认后再补足样本量到各标签50个

- **真实项目样本获取成本**：若暂时拿不到足够的真实历史任务，可先用登录故事v3（`登录故事-单任务实现清单v3-SpringBoot-PRonly.md`）或账号个人中心案例（`prompts/多故事迭代案例-账号与个人中心.md`，仍为Node技术栈历史文档，仅供任务结构参考）的任务清单展开出实现说明作为过渡样本，但要在结论里明确标注"部分样本非真实代码库/非当前技术栈，文件命中率维度结果需降权参考"

## T00103：业务规则——连续失败锁定

你要做的事：实现连续5次密码错误后锁定账号15分钟、锁定期满自动恢复的规则。
对应验收标准：AC-3（连续5次密码错误 → 锁定账号15分钟）

本任务信息自包含：不要假设除下文之外还有更多规划背景，下面就是执行这个任务所需的全部上下文。

### 背景
这是"用户名密码登录"纵向安全切片计划中的第3/6个任务。**前序任务T00101、T00102均尚未实际交付**。本说明基于规划预判展开，派发前需先确认两者已合并，尤其要核对`AuthService`的失败分支结构与`User`表的真实字段。本任务完成后，整体功能仍由`app.feature.login-auth-enabled`包裹，对用户不可见。

### 预计涉及文件

**必须改动**：
- `server/src/main/resources/schema.sql`（修改，`[INFER]`在T00101建立的`User`表定义之后追加`ALTER TABLE`语句）
- `server/src/main/java/com/tasksplitting/api/User.java`（修改，`[INFER]`record新增`failedLoginAttempts`/`lockedUntil`字段）
- `server/src/main/java/com/tasksplitting/api/UserRepository.java`（修改，`[INFER]`新增更新失败计数/锁定字段的方法）
- `server/src/main/java/com/tasksplitting/api/AuthService.java`（修改，`[INFER]`新增锁定态判断与计数递增逻辑）

**可能改动**：无。

### 技术选型

1. **schema变更方式** → 在`schema.sql`追加：
   ```sql
   ALTER TABLE "User" ADD COLUMN IF NOT EXISTS failedLoginAttempts INTEGER NOT NULL DEFAULT 0;
   ALTER TABLE "User" ADD COLUMN IF NOT EXISTS lockedUntil DATETIME;
   ```
   依据：延续T00101确立的"schema.sql累加式演进"全局约定（sqlite-jdbc 3.49.1.0捆绑的SQLite版本支持`ADD COLUMN IF NOT EXISTS`），不引入迁移工具。`[FACT]`引用T00101已确立的约定。
2. **锁定响应格式** → `423 Locked`状态码 + 响应体`{ "error": "ACCOUNT_LOCKED", "lockedUntil": "<ISO8601>" }`。依据：423是HTTP状态码注册表中精确对应"资源当前锁定"的语义；返回绝对时间戳而非预先算好的剩余秒数，避免网络延迟/客户端时钟漂移造成偏差。`[ASSUME]`

### 你要做什么

**后端**：
- `AuthService.login`中，在查到`User`之后、密码比对之前，先判断`lockedUntil`是否非空且晚于`LocalDateTime.now(clock)`：是则直接抛`AuthException("ACCOUNT_LOCKED", ...)`，不进行密码比对，不修改计数字段。
- 密码比对：错误时`failedLoginAttempts += 1`并写回`UserRepository`；若递增后达到5，在**同一次请求**内同时把`lockedUntil`设为`LocalDateTime.now(clock).plusMinutes(15)`并写回，本次响应直接返回`ACCOUNT_LOCKED`（而非`INVALID_PASSWORD`）；未达到5则按T00102逻辑返回`INVALID_PASSWORD`。
- 密码比对成功：登录成功前先把`failedLoginAttempts`重置为0。

### 从验收标准推导出的隐含规则
1. `[INFER]` 连续失败次数被一次成功登录打断后清零——AC-3使用"连续"一词，若成功登录不清零，"连续5次"会退化为历史累计，与字面语义矛盾。
2. `[INFER]` 锁定检查必须发生在密码比对之前——避免对已锁定账号做无意义的哈希比对运算。
3. `[INFER]` 锁定期内的重复请求不会延长/重置`lockedUntil`，也不会继续递增`failedLoginAttempts`。
4. `[INFER]` 触发锁定的第5次失败请求本身，响应应直接是`ACCOUNT_LOCKED`而非`INVALID_PASSWORD`。

### 明确不要做的事
- 不要实现"记住我"与会话时长差异化（属于T00104）
- 不要实现登录埋点，包括锁定事件的埋点（属于T00105）
- 不要修改flag状态
- 不要改动T00102已建立的`USER_NOT_FOUND`/`INVALID_PASSWORD`判断逻辑，只新增`ACCOUNT_LOCKED`这一条新分支
- 不要对`User`表做锁定字段之外的schema重构
- 若T00101、T00102尚未合并，暂停并报告

### 完成定义（DoD）
- `[FACT]` 连续5次密码错误后，第5次错误请求本身即返回423 + `ACCOUNT_LOCKED`，有集成测试覆盖。
- `[FACT]` 锁定状态下第6次及之后请求均返回423 + `ACCOUNT_LOCKED`，不执行密码比对，有测试覆盖。
- `[FACT]` 锁定响应体`lockedUntil`字段值约为触发锁定时刻+15分钟，有测试断言。
- `[INFER]` 用注入的固定`Clock`模拟"15分钟后"，正确密码可重新登录成功且`failedLoginAttempts`归零，有测试覆盖，不真实等待15分钟。
- `[INFER]` 错2次后登录成功，之后新的错误从0重新计数，有测试覆盖。
- `[INFER]` 锁定期内二次请求，`lockedUntil`与首次触发锁定时一致，有测试覆盖。
