# StackHarness —— 垂直技术栈智能研发 Harness 商业方案

> **一句话定位**：不做下一个 Cursor，做"Cursor 跑不起来的低成本替代层"——
> 通过**垂直技术栈（Vue/React + Java Spring）+ 精细化 SDD/规则库 + 17B/70B+ 显式路由 + 四道硬门禁兜底**，
> 让企业研发团队的 AI 编码账单从 20 万/月降到 3 万/月，且质量不塌。

---

## 一、机会判断：为什么是现在

### 1.1 技术前提已经成立

**Harness 的影响远大于换模型。** 2026 年编码 Agent 圈已形成共识：同一模型换 harness 带来的结果波动（约 ±22%）远大于换模型（约 ±1%）。

这意味着：
- 任务拆细 + SDD 写清 + 四道门禁兜底后，**17B 级模型（Qwen3-Coder 14B/32B，HumanEval 85-92%）在 CRUD/配置/单测/简单业务逻辑上，配合校验闭环，产出可达 70B+ 的 80-90% 质量**。
- 复杂任务（跨模块重构、算法、架构决策）路由到 70B+（Claude Sonnet/Opus、Qwen3.5-397B-A17B 等）。
- 成本差巨大：以 Qwen3-Coder 对比 Qwen3.5-397B-A17B 为例，blended 价格约 **$0.36/M vs $4.20/M，差 11 倍**；对比 Claude Opus 级闭源可达 **50-100 倍**。

**结论：瓶颈不在模型大小，而在 SDD 完备性与校验覆盖度。** SDD 写到"第 3 行写 `if (count > 0) return error`"的粒度时，17B 与 70B 输出几乎无差。

### 1.2 市场痛点真实且急迫

| 痛点 | 现状 | 我们的靶子 |
|---|---|---|
| 账单失控 | Copilot 转计量计费后重 Agent 用户账单涨 10-50 倍；微软取消内部 Claude Code 许可 | Uber"AI 生成 70% 代码但 4 个月烧 34 亿预算" |
| 质量不可控 | AI 写的并发/权限代码出事，无系统性校验 | 并发正确性、业务规约符合性无法靠人盯 |
| 审查疲劳 | 缺陷多、审查疲劳、不敢上生产 | "写完有闸门"而非"写完靠人盯" |

### 1.3 窗口期：2-3 年

- **大厂不做中间层**：Cursor/Devin 卖"自主 Agent"叙事，不会下沉做"低成本替代层"。
- **开源不细**：GitHub Spec Kit、Kiro、BMAD 均通用、不做技术栈精细化与显式模型路由。
- **窗口会收窄**：17-32B 模型能力持续上移，吃掉中低复杂度任务，**路由阈值需随代际重调，非一劳永逸**。

## 二、产品定义

### 2.1 产品名与一句话价值

**StackHarness** = **技术栈感知的 SDD + Guardrail Harness + 模型路由器**。

对用户的价值陈述：
> "把你们的 Vue3+React 前端、Java Spring 后端，配上一套写细的规则库和 SDD，
> 让 80% 的代码改动跑在本地 17B 上、20% 的硬骨头才上 70B+——
> 账单降到 1/5，且每笔改动都得过四道门禁才能合进主干。"

### 2.2 核心架构

```
┌──────────────────────────────────────────────┐
│            StackHarness 编排层                │
│  任务拆解 + 上下文管理 + 四道门禁 + 模型路由   │
├──────────────┬──────────────┬────────────────┤
│  简单任务      │  中等任务      │  复杂任务       │
│  (CRUD/配置)  │  (业务逻辑)    │  (架构/重构)    │
│  → 17B 本地   │  → 32B 云     │  → 70B+ 云     │
│  成本 ≈ 1     │  成本 ≈ 3     │  成本 ≈ 20     │
└──────────────┴──────────────┴────────────────┘
         ↓ 四道门禁（①生成前 ②生成中 ③提交前 ④合并前）
   本地先过再 push，未证明条目驱动下一轮测试
```

**关键设计**：模型路由不是黑盒，而是**显式策略**——拆解任务时根据标签（crud / logic / refactor / algo / arch）在 SDD 中注明所用模型档位，可审计、可调优。

### 2.3 与现有玩家的差异化卡位

| 玩家 | 定位 | 技术栈精细化 | 显式模型路由 | 硬门禁兜底 |
|---|---|---|---|---|
| GitHub Spec Kit | 通用 SDD 管道 | ❌ | ❌（agent 自选） | 部分 |
| Kiro | 通用 Agent IDE | ❌ | ❌ | 部分 |
| BMAD | 方法论 prompt 包 | ❌ | ❌ | ❌ |
| Devin / Cursor | 自主 Agent / IDE | ❌ | 内部黑盒 | 部分 |
| **StackHarness** | **垂直技术栈专用** | **✅ 预置规则库/测试模板** | **✅ 显式 17B/70B 策略** | **✅ 四道 + spec-verifier** |

**卡位一句话**：不做下一个 Cursor，做"Cursor 跑不起来的低成本替代层"。

## 三、技术壁垒拆解

### 3.1 四层资产（可积累、可复用）

| 资产层 | 内容 | 迁移性 |
|---|---|---|
| **L1 规则库（六类）** | 编码/安全/架构/业务/合规/性能，每条标注强制点与判定形态（A断言存在性/B行为验证/C禁止模式） | 跨项目复用率高 |
| **L2 SDD 模板** | Vue3/React/Spring Boot 3 的 constitution→spec→plan→tasks 骨架 | 技术栈绑定，最值钱 |
| **L3 测试与门禁模板** | 并发测试（CountDownLatch/k6）、spec-verifier MCP+CLI、pre-commit 配置 | 跨项目复用 |
| **L4 模型路由策略** | 任务标签 → 模型档位映射，按一次通过率动态调阈值 | 随模型代际更新 |

**押注硬门禁层**：规则库、规约、门禁脚本沉淀在 Git/CI 层，换 AI 工具（Cursor/Claude Code/换 DeepSeek 版本）时纹丝不动——这是"团队投入该押在哪"的答案。

### 3.2 六类规则的抽取与判定（产品化核心）

后三类（业务规约/合规红线/性能基线）无现成模板，产品提供**通用抽取方案**：

| 类别 | 来源 | 抽取方法 | 判定形态 |
|---|---|---|---|
| 业务规约 | PRD/用户故事/验收标准/**提示词** | LLM 抽取 + 可判定改写（枚举法/附加条件法/测量法） | A/B/C |
| 合规红线 | GDPR/等保 2.0/行业监管 | 法条分解 → 原子约束 → 检测点 + 关键词矩阵 | A/C + 人工复核 |
| 性能基线 | SLA/SLO/APM 历史/压测报告 | 阈值提取 + 趋势建模（P99/P50） | B（趋势检测） |

**可判定改写示例**（"每人限领一张" → R-BIZ-002）：
> 同一 `user_id` + `coupon_id` 在 `coupon_claims` 表中记录数 ≤ 1（枚举法）
> 并发 N 次请求，新增行数必须 = 1（附加条件法 → 判定形态 B，需真实跑并发测试）

### 3.3 spec-verifier：差异化技术点

把"实现是否忠于规约"从**靠人读**变成**一道可自动判定的门禁**：
- **MCP-in-loop（软门禁②）**：让 AI 即时自纠，95% 违规零摩擦消化
- **pre-commit/CI（硬门禁③）**：确保逃逸的不会漏过，兜底保障
- **共用一套内核**：MCP server 与 CLI 两种外壳，规则绝不写两套

**指标双轨**：
- **loop 自愈率** > 80%（说明编排与 prompt 设计好）
- **pre-commit 拦截率** < 20%（说明体验流畅、软门禁有效）

## 四、目标客户与市场

### 4.1 客户画像（按优先级）

| 优先级 | 客户类型 | 痛点强度 | 付费意愿 | 切入方式 |
|---|---|---|---|---|
| P0 | 中大型互联网/金融研发团队 | 极高（账单+合规） | 高 | 私有化部署 + 定制规则库 |
| P1 | 外包/定制化软件公司 | 高（人力成本敏感） | 中高 | 技术栈模板 + seat 授权 |
| P2 | 中小创业团队 | 中（账单敏感） | 中 | SaaS 托管 + 按量阶梯 |

### 4.2 技术栈选择逻辑

**为什么是 Vue/React + Java Spring？**
- 国内最主流前后端组合，存量项目海量
- 组件化、分层清晰，**规则易于穷举、校验点密集**
- 企业合规要求高（金融/政务/医疗），**硬门禁需求刚性**

后续可扩展：Go、Python（FastAPI/Django）、小程序/Flutter 等。

### 4.3 市场空间估算（量级判断）

- **TAM**：全球 AI 编码工具市场 2026 年数百亿美元级，且高速增长
- **SAM**：中国企业级研发团队中，采用 Vue/Java 技术栈且对成本敏感的部分，约数十亿 RMB/年
- **SOM（3 年目标）**：切 1-3% 份额，对应千万级 ARR——**先验证单位经济性，再谈规模**

## 五、商业模式

### 5.1 三层变现（按 ROI 排序）

| 层级 | 形态 | 收费方式 | 毛利 | 说明 |
|---|---|---|---|---|
| **L1 企业内效/私有化** | 给甲方做"Vue+Java 专用 harness" | 项目制（30-80 万/项目）+ 年度维护 | 高 | **最稳，先打标杆** |
| **L2 技术栈模板市场** | 规则库 + SDD 模板 + 路由策略包 | 订阅（按 seat 5-20 万/年） | 极高 | 复用 L1 沉淀，边际成本近零 |
| **L3 托管式混合推理 SaaS** | 接入仓库，自动 17B/70B 路由 | 按节省成本分成（省 1 收 0.3） | 中→高 | 最性感但最重，后做 |

**推荐路径**：L1 打样 → L2 产品化 → L3 平台化。**先用咨询养产品，再用产品放大。**

### 5.2 单位经济性（示意）

假设客户：100 人研发团队，原纯 70B 方案月账单 20 万。

| 项目 | 金额/月 | 说明 |
|---|---|---|
| 原账单（纯 70B） | 20 万 | 基线 |
| StackHarness 方案 | 3-4 万 | 80% 走 17B（本地近零）+ 20% 走 70B |
| **客户节省** | **16-17 万** | 账单降到 1/5~1/6 |
| 我方收费（节省的 30%） | ~5 万/月 | 或 seat 订阅打包 |
| 我方成本（平台/支持） | ~1 万 | 边际成本随规模下降 |

**ROI 对客户立即可见**：投入回收期 < 3 个月。

## 六、落地路线图

### 6.1 阶段划分

| 阶段 | 时间 | 目标 | 交付物 |
|---|---|---|---|
| **Phase 0：自证** | 0-2 月 | 跑出真实成本比数据 | 团队内部 2 周实测：17B 一次通过率 + 成本压缩比 |
| **Phase 1：标杆** | 2-6 月 | 拿下 2-3 个 P0 客户 | L1 私有化项目 + 客户背书 + 规则库沉淀 |
| **Phase 2：产品化** | 6-12 月 | L2 模板市场上线 | Vue3+Spring 规则库 v1、路由决策树、文档 |
| **Phase 3：平台化** | 12-24 月 | L3 SaaS 内测 | 托管推理 + 仪表盘（自愈率/拦截率/节省额） |

### 6.2 Phase 0 必做的两个验证数字

**这两个数字决定整个方案是否成立，务必先拿到再投入：**

1. **17B 一次通过率**
   - Vue 组件 + Spring 接口各抽 50 个**真实任务**
   - 看 spec-verifier 一次绿的比例
   - **≥ 80% → 可推；< 60% → SDD 还需细化或拆解策略要改**

2. **成本压缩比**
   - 同批任务分别用"纯 70B"和"17B+校验+20% 升级 70B"跑
   - 算 token 账单比
   - **≥ 1:5 且缺陷密度不显著上升 → 销售故事立得住**

### 6.3 交付物清单（Phase 1-2）

- `rules/`：六类规则 YAML（被 MCP/CLI 共用读取）
- `spec-verifier-core`：规则加载器 + 分类分发器 + 三种判定形态执行器
- `spec-verifier-mcp`：loop 内软门禁（check_diff / pending_items / prove_item）
- `spec-verifier-cli`：pre-commit/CI 硬门禁
- SDD 模板：constitution / spec / plan / tasks 骨架（Vue3+React+Spring Boot 3）
- 并发测试模板：CountDownLatch / k6 / Python ThreadPoolExecutor
- **模型路由决策树**（见附录）

## 七、竞争与风险

### 7.1 竞争应对

| 对手类型 | 应对策略 |
|---|---|
| 大厂（Cursor/Devin/阿里 Qoder） | 不打自主叙事，打"成本敏感层的开箱专用包"；大厂锁通用层，我们锁垂直层 |
| 开源（Spec Kit/Kiro/BMAD） | 兼容并蓄——基于 MIT 协议二次增强，规则库/测试模板做商业化增值 |
| 同层创业 | 用"真实客户数据 + 规则库厚度"筑壁垒，先发优势 |

### 7.2 四大风险与对冲

| 风险 | 影响 | 对冲策略 |
|---|---|---|
| **SDD 编写成本高** | 前期人力投入大，客户不愿付 | 抽取脚本化（规则库六类抽取 Prompt 模板）、模板复用、用 LLM 辅助抽取 |
| **模型能力上移** | 路由阈值需重调 | 路由策略做成数据驱动，随模型代际自动校准阈值 |
| **规则库维护负担** | 框架/语言升级需同步 | 规则版本化管理，社区共建 + 自动检测过时规则 |
| **客户数据安全** | 企业不愿代码出域 | **默认私有化部署，17B 本地运行**，仅 70B 部分可选云 |

### 7.3 护城河在哪

**真正难复制的不是 harness 代码，而是**：
1. **垂直技术栈的规则库厚度**（数千条经生产验证的规则 + 并发测试模板）
2. **真实项目的 SDD 化经验**（把遗留系统规约化的咨询能力）
3. **路由策略的实测数据**（哪个标签该用哪个档位，来自真实账单）

这三者都需要**客户项目持续喂养**，先发者越跑越厚。

## 九、结论

**StackHarness 有市场机会，但不是"做个 harness 就能收割"，而是：**

> **"特定技术栈（Vue/React + Java）+ 精细化 SDD/规则库 + 17B/70B 显式路由 + 四道硬门禁兜底"的组合包，在企业成本敏感层有 2-3 年窗口期。**

**机会大小取决于三件事**：
1. 能否把 **SDD 编写成本**压到最低（规则库抽取脚本化、模板复用）
2. 能否在自己团队**先跑出 1:5 成本比的真实数据**
3. 能否用 **L1 咨询项目持续喂养 L2 规则库**，筑起厚度壁垒

**下一步行动**：立即启动 Phase 0——用两周时间在自有项目上验证"17B 一次通过率"与"成本压缩比"两个数字。这两个数字成立，方案即具备对外融资/销售的完整说服力。

## 附录 A：模型路由决策树

```
任务标签判定（拆解阶段由 SDD/编排器标注）
│
├─ crud / config / test-generation / simple-ui
│   → 17B（本地，成本 ≈ 1）  ✅ 目标覆盖 80%
│
├─ business-logic（多分支/状态机/中等复杂度）
│   → 32B（云，成本 ≈ 3）
│
├─ refactor / integration（跨模块）
│   → 70B+（云，成本 ≈ 20）
│
├─ algorithm / novel-design / performance-tuning
│   → 70B+（云）+ 人工架构评审
│
└─ 兜底规则
    · 17B 连续 3 轮 spec-verifier 未通过 → 自动升级一档
    · 涉及合规红线（R-COMP-*）→ 强制 70B+ 且人工审查
    · 核心链路（覆盖率 ≥ 85%）→ 不低于 32B
```

**动态调整机制**：每月根据"一次通过率"重算路由阈值——
- 若 17B 某标签通过率 > 90%，可将该类任务永久下沉至 17B
- 若 < 70%，则该标签升级或回退人工

## 附录 B：四道门禁与规则强制点对照

| 门禁 | 强制力 | 典型规则 |
|---|---|---|
| ① 生成前规则 | ⚠️ 软（可跳过） | R-CODING / R-SEC / R-COMP |
| ② 生成中校验 | ⚠️ 软（Hook 辅助） | R-TYPE / R-TEST / R-SPEC |
| ③ 提交前门禁 | ✅ **硬** | R-PRE（含 spec-verifier） |
| ④ 合并前审查 | ✅ **硬（人审）** | R-MR / R-HUMAN |

**原则**：每条规则必然挂在 ③ 或 ④ 之一——纯软门禁的规则等于建议，不具约束力。
