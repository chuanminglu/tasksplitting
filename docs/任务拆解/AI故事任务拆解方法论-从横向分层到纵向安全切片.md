# 故事任务拆解方法论：从"按技术层拆"到"按安全切片拆"

> 定位：这是一份方法论整理文档，用于重构 Deerpowers AI DevOps Skills 框架里"故事拆解任务"相关的 Skill。
> 起点：原有做法把一个故事（如"登录"）拆成"前端开发 / 后端开发 / Mock（如需要） / 测试"，本质是**按技术层横向拆分**。本文整理为什么要转向**纵向安全切片**，具体怎么切，以及这套切片怎么贯穿到CI/CD和对外发布的全流程。

---

## 0. 结论先行

> **拆分的主轴，应该从"这是什么技术层的活"，换成"这一刀切下去，切出来的东西能不能被独立验证、独立安全合并"。**

原有的"前端/后端/Mock/测试"不是错的直觉，但被放在了错误的层级——它们不应该是**顶层任务类别**，而应该是**某个纵向切片内部的实现细节**。Mock 尤其如此：它不是一个独立任务，而是"契约先行并行开发"技术，本质上是 Expand-Contract 模式在团队协作边界上的特例。

再往后延伸一层结论：**代码合并到主干**和**功能对用户发布**是两件解耦的事，解耦的机制是**特性开关**——批准的PR应该立刻合并，不需要等整个故事做完；而故事真正"对外发布"，是合并完成之后的另一个独立决策点。

---

## 1. 原有拆法的问题诊断

"前端开发 → 后端开发 → （如需要）Mock → 测试"这种**横向按层拆分（Horizontal Slice）**，在AI编码时代会放大三个问题：

| 问题                                 | 具体表现                                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **集成滞后**                   | 前端和后端分别做完才对接，契约不匹配的风险堆到最后才暴露，而不是每个切片就验证一次                                         |
| **子任务本身没有独立业务价值** | "后端开发"做完，什么都不能演示、不能发布——这正是"任务级别没有业务价值"的具体表现，只是它出现在层级拆分而不是故事拆分层面 |
| **PR 体积不可控**              | AI 辅助下"后端开发"这一个任务很容易一次产出一个大PR，评审跟不上——小批量提交纪律要解决的问题，按层拆不会主动导向小PR      |

**核心转变**：从横向切片转向**纵向切片（Vertical Slice）**——每个切片都是一条端到端的最小可验证路径，前端、后端、测试都包含在同一个切片里，只是"薄"，不是"缺层"。

---

## 2. 判断规则：先选宏观模式，再谈怎么切

> **这个故事有没有"已经在生产环境跑着、不能说停就停"的旧行为？**
>
> - **没有** → Walking Skeleton（骨架先跑通）+ 特性开关
> - **有** → Expand-Contract（Parallel Change）

两者的共同底层逻辑：**先分离"能安全合并到主干"和"对用户真正可见"，再决定合并顺序**。这条规则也解释了为什么不能把两个模式混用或二选一定死——它们是针对不同变更性质的正确选择，选错模式（比如对已上线行为做法当新功能"一次性切换"）就会引入不必要的风险。

### 2.1 模式A：Walking Skeleton + 特性开关（新增能力）

来源：Alistair Cockburn 提出的"Walking Skeleton"，配合 Feature Flag（Pete Hodgson / Martin Fowler）实现"合并"与"可见"解耦。

**做法**：先搭一条最薄的端到端路径（哪怕丑、哪怕功能不全），确保架构各层真的能打通；再逐个切片"加厚"——每个加厚切片都是独立PR、独立可测，全程可以合在flag后面不对用户可见，最后一次flag切换才真正开放。

### 2.2 模式B：Expand-Contract / Parallel Change（变更已上线行为）

来源：Martin Fowler（ThoughtWorks）提出的 Parallel Change 模式，也称 Expand-Contract，是 Branch by Abstraction、Strangler Fig 等一系列"渐进式安全迁移"模式的核心思想。

**三阶段**：

| 阶段                       | 做什么                                                                 | 风险特征                                                   |
| -------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------- |
| **Expand（扩张）**   | 新增新实现路径/字段/接口版本，与旧实现**并存**，旧调用方完全无感 | 只加不删，风险最低，可以先合主干                           |
| **Migrate（迁移）**  | 调用方逐个/逐群切到新路径，通常伴随双写双读或灰度对比                  | 可按"调用方"或"用户分群"拆成多个独立PR，每个只切一部分流量 |
| **Contract（收缩）** | 确认没有调用方再依赖旧路径后，删除旧代码                               | 纯删除，但必须等观测周期结束才能做，不能提前               |

## 3. 重新定位 Mock：契约先行的并行开发技术

这是本次整理里最关键的一个重新框定：

> **"前端 + 后端 + Mock"并行开发，本质上就是 Expand-Contract 模式，只是应用在"团队协作边界"而不是"生产环境迁移边界"上。**

| Expand-Contract 阶段 | 对应到"前端 + Mock + 后端"场景                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Expand**     | 先定契约（如 OpenAPI/接口契约），后端按契约实现真实接口，前端按同一契约实现 Mock——两者同时开工，互不阻塞 |
| **Migrate**    | 前端把调用从 Mock 切到真实后端接口——这就是"集成"，与"调用方切到新实现"是同一个动作                       |
| **Contract**   | 确认集成没问题后，删除/关闭 Mock——与"删除旧实现"是同一个动作                                             |

**结论**：Mock 不该是顶层任务，而是某个纵向切片内部、为了让前后端并行而采用的具体实现技术。真正配套的工程实践是**契约先行（Contract-First）/ 消费者驱动契约（Consumer-Driven Contracts，如 Pact 框架）**——先把契约定清楚、写成契约测试，前后端才能真正放心并行，而不是"各自猜对方会怎么实现"。

### 3.1 层内分工怎么处理

前端/后端不再是顶层任务，而是"在某个切片内部谁干哪部分"的分工描述。例如"切片1：极简登录跑通"这一个任务内部，才需要区分"后端：签发 token 的最小实现""前端：调用登录接口 + 跳转"。

### 3.2 测试要内嵌，不是最后一个阶段

测试不是"最后一个阶段"，而是每个切片的**完成定义（Definition of Done）的一部分**——切片没有对应测试，这个切片就不算完成，不能进入下一个切片。这与测试域"从全量回归转向变更感知"的精神一致：验证要跟着变更走，不要攒到最后一次性做。

## 4. 纵向切片的具体刀法（怎么切）

宏观模式决定"选哪条路"，下面这些是决定"路上怎么一步步走"的具体技巧，源自 Henrik Kniberg《How to Split a User Story》一文总结的经典切分模式，可组合使用：

| 切分技巧                   | 说明                                                                      |
| -------------------------- | ------------------------------------------------------------------------- |
| 按工作流步骤切             | 先做最简单的一条通路，再逐步补齐流程中的其他步骤                          |
| 按业务规则变化切           | 先做一种规则/方式，再加其他变体（如先支持用户名密码登录，再加验证码登录） |
| 按数据/输入变体切          | 先支持一种客户端/输入形式，再扩展其他形式                                 |
| 按 CRUD 操作切             | 涉及数据管理时，先做查询，再做增删改                                      |
| 按 happy path / 异常路径切 | 先跑通主路径，异常处理和边界场景作为后续切片                              |
| 延迟非核心工作             | 性能优化、UI 打磨、埋点统计放到最后的切片，不阻塞核心路径验证             |

## 5. 登录案例完整演练（新旧拆法对比）

### 版本A：全新登录功能（无旧行为，走 Walking Skeleton）

**旧拆法（按层）**：① 前端登录页 ② 后端登录接口 ③ Mock（前端等后端时用）④ 测试
问题：前端和后端各自做完才对接；"后端登录接口"一个任务可能覆盖校验、限流、会话管理全部逻辑，PR容易一次性偏大。

**新拆法（纵向切片，Walking Skeleton）**：

1. 切片1：用户名密码登录成功后拿到最简 token，全程在 flag 后，用户不可见（内含：最小后端签发逻辑 + 最小前端调用 + 对应单测）
2. 切片2：加输入校验与错误提示（密码错 / 账号不存在）
3. 切片3：加登录失败次数限制 / 防暴力破解
4. 切片4：加"记住我" / 多设备会话管理
5. 切片5：UI 打磨、埋点，flag 开放给真实用户

每个切片都是独立小PR，独立可测，前后端工作都在切片内部完成——不再有单独的"前端任务"或"后端任务"。

### 版本B：改造已有登录机制（有旧行为，走 Expand-Contract）

场景：登录会话机制从 Session 升级为 JWT，Web端和已发布的手机APP旧版本都不能中断登录。

**旧拆法（按层）会怎么拆很危险**——很可能是"① 后端改造JWT ② 前端适配JWT ③ 测试"，看起来合理，但隐含了"一次性切换"的假设，一旦APP旧版本还在线上跑，直接会切断旧客户端。

**新拆法（Expand-Contract）**：

1. **Expand**：新增JWT签发+校验中间件，与Session并存；登录成功后同时返回Session Cookie和JWT，旧APP版本无感继续用Session（内含后端实现+对应契约测试）
2. **Migrate-1**：Web端切到JWT校验路径，观察一段时间（内含前端适配+集成测试）
3. **Migrate-2**：APP按版本灰度切换（因APP升级滞后，天然分批，每批一个独立PR）
4. **Contract**：确认无客户端依赖Session后，删除Session签发与校验代码

**关键差异**：新拆法把"能不能安全切换"作为拆分主轴，旧拆法把"这是前端还是后端的活"作为拆分主轴——后者在新增场景下会导致集成滞后，在改造场景下会掩盖"不能一次性切换"的真实风险。

## 6. 完整分层关系图

把本文与此前"故事拆小 ≠ PR拆小"的讨论结论一并串起来：

```
第1层 · Story（业务价值层，INVEST判断）
   故事本身要小、要独立可验证、要有业务价值
        ↓
第2层 · 宏观模式选择（安全集成层）
   问："有没有不能停的旧行为？"
   → 没有：Walking Skeleton   → 有：Expand-Contract
        ↓
第3层 · 纵向切片排序（Kniberg切分技巧，决定切片顺序）
   工作流步骤 / 业务规则 / happy-unhappy path / 数据变体 ...
        ↓
第4层 · PR/提交与CICD纪律（评审安全层）
   每个切片 = 一个小PR，前后端工作 + 对应测试都在切片内完成
   （Mock是切片内部"契约先行并行开发"的实现技术，不是独立任务）
```

- 第1层解决"值不值得做"
- 第2层+第3层解决"这个故事的实现顺序该怎么安全推进"
- 第4层解决"每一步合并是否安全、评审跟不跟得上"

三层各管一件事，缺一层都不完整；也因此，"故事拆小"和"小批量提交纪律"不能互相替代（见本系列上一篇讨论）。

**衔接下文**：第4层解决的是"合并到主干安不安全"，但没有回答"用户什么时候能看到这个功能"——这是第7、8节要补上的部分。

## 7. 特性开关（Feature Flag）：是什么、怎么实现

**定义**：用外部可配置的条件，而不是靠重新部署代码，来决定某段代码路径是否生效。它把"**部署（Deploy）**"和"**发布（Release）**"这两件事解耦——代码可以先部署到生产环境，功能对用户保持关闭，等真正要对外开放时，只需要翻一下开关，不需要再发一次版本。

来源：Pete Hodgson，发表于 martinfowler.com，"Feature Toggles (aka Feature Flags)"。

### 7.1 四种类型（治理规则不一样，不要混用同一套标准）

| 类型                     | 用途                                                             | 生命周期                       |
| ------------------------ | ---------------------------------------------------------------- | ------------------------------ |
| **Release Toggle** | 隐藏未完成功能，配合 Walking Skeleton / Expand-Contract 逐步加厚 | 短命——功能全量发布后必须删除 |
| Experiment Toggle        | A/B测试，比较不同实现的效果                                      | 实验结束后删除                 |
| Ops Toggle               | 运维熔断/降级开关，出问题时快速关闭某功能                        | 可能长期保留                   |
| Permission Toggle        | 按付费等级/租户开放功能                                          | 长期保留，是业务规则的一部分   |

本文讨论的故事拆解场景，用的都是**Release Toggle**——这一点很重要：Release Toggle是唯一"设计上就要被删除"的开关，如果不清理，代码里会堆积越来越多的死分支，形成"**开关债务（Flag Debt）**"。

### 7.2 最简实现（能跑起来的最小版本）

```
if (featureFlags.isEnabled("new-login-jwt", userContext)) {
    // 新路径：Expand阶段新增的实现
} else {
    // 旧路径：仍在服务未迁移的调用方
}
```

- **最简单**：一个配置文件/环境变量里的布尔值，代码里读取并判断
- **进阶**：接入专门的开关管理服务（如 LaunchDarkly、Unleash、Flagsmith 等开源/商业方案，或团队自建配置中心），获得：
  - 不重新部署即可切换（配置中心推送，服务端实时读取）
  - 按用户分群/百分比定向（是灰度发布的基础设施）
  - 操作留痕（谁在什么时候翻了哪个开关）

### 7.3 治理规则（避免开关本身变成技术债）

- 每个 Release Toggle 必须有**明确的负责人和预期删除时间**
- 功能全量发布并观察稳定后，**删除开关和对应的旧代码分支**——这一步就是 Expand-Contract 里的 Contract 阶段，也是"切片"生命周期真正结束的标志
- 定期扫描代码里"存活超过预期时间"的开关，作为技术债跟踪项，纳入迭代计划

## 8. 故事级发布：怎么从"切片合并"走到"对外发布"

回答开头的问题：**故事级发布不是等所有切片任务都做完才合并**——切片合并和故事发布是两件解耦的事，解耦的机制正是第7节的特性开关。

### 8.1 两条时间线是分开的

```
代码合并时间线（连续、频繁、小批量）：
  切片1 PR合并 → 切片2 PR合并 → 切片3 PR合并 → ... → 切片N PR合并
  （全程 flag=off，代码已经在生产环境里，但用户看不到）

故事发布时间线（离散、有决策点）：
  全部切片合并完成 + 验收标准满足 → flag翻转 → 灰度放量 → 观察 → 全量 → 删除开关
```

### 8.2 故事级"可以翻开关"的判断标准（Definition of Done at Story level）

- 组成该故事的所有切片PR都已合并到主干
- 每个切片对应的自动化测试（单测/契约测试/集成测试）全部通过
- 在预发布/灰度环境用 flag=on 跑过一次完整验收（对应故事最初的验收标准，即 INVEST 里的"Testable"）
- 有对应的可观测手段就位——至少要能判断"翻开关之后是否出问题"

### 8.3 翻开关不是"一步到位"，也要小批量

跟合并代码要小批量一样，**对用户开放功能也要小批量**，常见两种放量方式：

| 方式                                  | 做法                                                  | 适合场景                               |
| ------------------------------------- | ----------------------------------------------------- | -------------------------------------- |
| **百分比灰度（Canary）**        | 先对1%流量打开，观察指标，逐步5%→20%→50%→100%      | 面向海量C端用户，可以按流量比例切      |
| **环形发布（Ring Deployment）** | 先对内部员工/白名单用户开放，再到Beta用户群，最后全量 | 面向B端/企业客户，或需要人工反馈的场景 |

无论哪种方式，都要配合监控/告警（对应AIOps闭环），一旦异常指标触发，直接把开关**翻回off**——这是比"回滚代码"快得多的应急手段：不需要重新部署，秒级生效，是特性开关相对纯代码回滚的核心优势。

### 8.4 全量稳定后，别忘了Contract

放量到100%并观察稳定一段时间后，故事才算真正"发布完成"——但还有最后一步容易被漏掉：**删除开关和对应的旧代码路径**（Expand-Contract 的 Contract 阶段）。这一步本身也应该是一个独立的小PR，不要和其他改动混在一起。

## 9. 完整CI/CD流程：从切片PR到故事发布

把前面所有结论串成一张贯穿"提交-构建-测试-部署-发布-回收"的完整流程图：

```
【切片级 · 持续集成 CI】（对应第6节第4层，高频、小批量）
  开发者提交切片PR（flag包裹，未完成时对用户不可见）
        ↓
  AI代码预审 + 静态分析（代码层质量门）
        ↓
  自动构建（构建层）
        ↓
  测试影响分析 → 只跑必要的自动化测试：单测 / 契约测试 / 集成测试（测试层）
        ↓
  人工评审（高风险改动必须有人复核）
        ↓
  批准即合并到主干，合并后立即删除分支 —— 不等其他任务

【切片级 · 持续部署 CD】（合并后自动触发，flag仍为off）
  主干构建产出部署包
        ↓
  自动部署到生产环境（部署层）—— 代码已上线，但flag=off，用户无感
        ↓
  重复以上流程，直到该故事的所有切片都已合并并部署

【故事级 · 发布决策】（离散决策点，不是自动触发）
  验收 Definition of Done（第8.2节标准）
        ↓
  翻转 Feature Flag（配置中心推送，不需要重新部署）
        ↓
  灰度放量：Canary百分比 或 Ring环形发布（第8.3节）
        ↓
  AIOps监控观察 —— 异常 → 秒级翻回flag=off（运维层）
                 —— 正常 → 继续放量至100%

【故事级 · 收尾】
  100%放量并稳定观察一段时间后
        ↓
  提交Contract清理PR：删除开关 + 删除旧代码路径
        ↓
  故事正式关闭
```

这张图把三个原本分开讨论的机制缝合到一起：**小批量提交纪律发生在"切片级CI"这一层，特性开关发生在"切片部署"和"故事发布"之间的解耦点，Expand-Contract的Contract阶段则是整个故事生命周期真正的收尾动作**——缺了任何一环，前面辛苦拆的纵向切片都会在发布环节被打回大批量操作的老路。

## 10. 常见反模式清单

| 反模式                                                     | 问题                                                                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 顶层按"前端/后端/测试"拆任务                               | 横向切片，集成滞后，子任务无独立价值                                                                                     |
| 把 Mock 当成独立任务立项                                   | 丢失了"Mock是契约先行技术"这一本质，容易脱离真实契约演进                                                                 |
| 测试作为最后一个阶段                                       | 验证滞后于变更，回归成本随代码库规模增长而非变更范围增长                                                                 |
| 对已上线行为做"一次性切换"                                 | 该用 Expand-Contract 的场景被当成 Walking Skeleton 处理，破坏兼容性                                                      |
| 对全新功能强套 Expand-Contract                             | 找不到"旧"可以并存/收缩，模式套用错位                                                                                    |
| 用"故事已经很小"代替 PR 小批量纪律                         | 混淆业务价值维度与集成安全维度，AI高产出下PR仍可能膨胀                                                                   |
| **批准的PR先不合并，攒着等全部任务做完再一次性合并** | **重新引入长分支、大批量合并的风险，切片拆分的价值被抵消——正确做法是"批准就合，合完就删；不要囤着等全做完再合"** |
| Feature Flag 翻到100%后忘记清理                            | 开关债务（Flag Debt）累积，代码里堆积越来越多死分支，可维护性下降                                                        |
